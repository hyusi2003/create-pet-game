# 游戏完成后接入产品

制作完成包含成品、封面、目录登记和用户入口验证。用户只要求独立 HTML 时交付便携文件；用户已经要求「直接导入产品 / 放进传 vibe / 逗一下」时，在可访问的目标环境完成本机接入，不反复询问已经授权的步骤。

用户同时制作了自定义形象时，先按 [自定义形象接入](appearance-import.md) 完成外观包转换、外观库导入及已授权的换上，再验游戏读取。形象包和游戏 HTML 使用各自的入口与契约，不能将 `prepare-vibe-import.mjs` 用作形象安装器。

先按 [热更新导入避坑](live-import.md) 识别运行实例。普通 HTML 导入即可打开，加入游戏库还需下述登记；内容导入不得把重启作为用户生效步骤。

## 准备便携导入材料

从最终构建 HTML 的实际绘制画面取封面，裁成与目标游戏卡片一致的比例；优先 WebP，也接受 PNG/JPEG。封面不得暴露私人角色/姓名；公开投稿时另核对素材权利。不要用源码截图、无关图或还没实现的效果作封面。

```sh
node <skill>/scripts/validate-game.mjs ./dist/my-game.html
node <skill>/scripts/prepare-vibe-import.mjs \
  --html ./dist/my-game.html --poster ./dist/cover.webp \
  --output ./delivery/my-game --id my-game \
  --title "我的游戏" --description "和搭子一起玩"
```

`<skill>` 是当前技能目录。输出目录必须不存在；工具不会覆盖旧交付。工具按字节原样复制 HTML/封面并生成 `catalog-entry.json` 与 `receipt.json`，包含资源名、SHA-256 和字节数，不写入本机来源路径。它执行本技能的双人 LAN 静态校验和图片类型/大小检查；**不验证玩法、图片完整解码或产品登记**。实际解码与真实宿主测试仍需完成。

条目固定为 `category:games`、`kind:game`，含 `id/title/description/file/poster/sha256/posterSha256`；`source/posterSource` 是相对于制作素材根目录的路径。接入时根据宿主当前规范调整来源字段，但不要改动成品字节或混用旧哈希。修改游戏/封面后重新生成一份新目录。

## 有宿主开发检出时直接登记

先读取目标检出的 AGENTS.md/CLAUDE.md、目录契约、资源导入/打包脚本和实际运行环境。以下是吐梨邦当前目录结构的接入方法，不要求普通制作者获取私有源码。

1. 找到目标实例实际使用的目录、素材根和缓存，确认是用户授权的开发/测试环境。检出目录、安装包内 ASAR、后台副本可能不同；改了某个 checkout 不代表正在运行的实例读它。不启动两个共享资料目录的实例。
2. 将 `catalog-entry.json` 合并到 `demo/core/vibe/catalog.json` 的 `items`，唯一 id、文件名与海报名不得碰撞。更新既有游戏则保留 id、发布新文件哈希。先准备候选目录，不先向运行中目录写半条数据。
3. 原样放置两个资源到 `assets/vibe/`，保留旧条目及其他资源；重建完整 `assets/vibe/manifest.json`，包含全部已登记资源的字节与哈希。沿用宿主的资源校验/打包函数，不能把单款的 `receipt.json` 当成整个产品 manifest。目录、资源、回执须一起进入版本控制，沿用宿主 Git LFS 规则，验证读取到真实字节而非 LFS 指针。
4. 开发环境若使用 `PET_VIBE_SOURCE_DIR` / `.vibe-local.json` 的 `sourceRoot`，将两个资源放到该根下条目指定的相对路径，或通过宿主已验证的缓存导入通道准备它们。**开发服务不一定直接读 `assets/vibe`**，只复制那里可能只有卡片而无法准备/播放。缓存对象按 `sha256 + 扩展名` 固定，检查宿主规范并验证实际读取；缓存应在 Git 外。
5. 当前宿主 `demo/scripts/import-vibe-resources.js`（`npm run vibe:import -- <完整素材根>`）导入的是整个目录，要求其他条目的素材/缓存也齐全，并会重建目标资源目录；它不会自动登记新 id。不要把只有一款游戏的材料目录交给它，不能因此丢失其他作品。打包链 `demo/scripts/bundle-vibe-resources.js` 从目录固定的资源重建并核对全量回执。
6. 资源全部校验就绪后，在同目录临时文件写出完整候选目录，再原子替换目录文件。运行实例具备目录热加载时，已打开列表自动显示，重新进入也刷新；旧客户端缺能力时报告兼容缺口并单独处理版本升级，不能把重启当作内容导入成功。只读安装包的内置目录仍需宿主正常升级，没有凭空的远程目录发布能力。不要主动重启用户日常实例，也不要修改签名安装包。

局部更新不修改 HTML/work SDK、账号、好友或插件市场；如果发现确需新增宿主能力，另列具体兼容需求，不能默认为接入作品顺手扩展内核。导入本机不等于允许公开发布、向好友发送、推送宿主或发安装包；只有用户已经授权的动作才继续执行。

## 实际入口验收

- 在真实运行宿主打开「传 vibe → 逗 TA 一下 → 游戏」，看到新卡片、正确标题和真实解码的封面；没有误开播放器盖住收件人页。
- 选择游戏、选人、「发送并一起玩」：实际准备/发送的文件哈希与导入成品一致，对端实际收到同一字节。双方按宿主提示接受邀请与能力授权；当前宿主可能自动完成设备信任，不能硬编码必须出现旧配对码。
- 两端显示各自当前宠物，双方准备后用真实操作完成一局、同一结算、再开及退出。卡片出现不是联机通过。
- 对具备热加载的实例，在同一列表打开期间新增/更新标题和封面并观察；编辑草稿不重置，已准备作品仍固定原字节，进行中的对局不中断。内容更新不能把旧附件自动换成新版本。
- 自动 Electron 验证使用隔离资料目录、独立 CDP 端口，窗口首次绘制前隐藏；用真实输入与 CDP 断言，背景截图确认实际画面，清理仅本轮测试进程。物理双机/原生鼠标等未覆盖时明确写出。

玩法、关卡、计分和结算的专用测试留在游戏项目中登记具名入口与聚合门禁；宿主保留目录/摘要、收发、授权、SDK/会话、窗口/生命周期等通用契约测试。使用真实游戏做接入样本时，显式选定版本，宿主断言只覆盖宿主责任；不要把该游戏的整套玩法回归复制进宿主。

真实宿主没有可用环境时仍完成便携材料、静态与浏览器检查，报告「材料已准备，产品登记/真实联机待验证」，注明缺少的环境。不要臆造客户端最低版本、下载地址或通过记录。

交付记录写清成品/封面哈希、产品入口、实际修改位置与验证结果。面向公开 PR/Release 只发布已审查的技能文件、公共引用和匿名测试结果，不附私人角色、宿主安装包、更新源、下载位置或本机资料。
